Join semantics in PySpark match SQL (see [SQL joins](/sql/joins/)), but on a cluster the semantics are only half the story. The other half is **how** Spark brings matching rows together: by copying a small table to every executor, or by shuffling both sides across the network. That choice usually decides whether a pipeline takes minutes or hours, and it is the most common Spark performance topic in interviews.

## Sample data and helpers

`orders` has an order for a customer that does not exist (9) and one with no customer (NULL); `customers` has a customer with no orders (3) and one with a NULL key. Two helpers print plans without the noisy expression IDs, and pull out the join strategy name.

```python
import tempfile, re, io, contextlib
from pyspark.sql import SparkSession, functions as F

warehouse = tempfile.mkdtemp()
spark = (SparkSession.builder.master("local[2]").appName("joins")
         .config("spark.sql.warehouse.dir", warehouse)
         .config("spark.sql.shuffle.partitions", "4")
         .getOrCreate())
spark.sparkContext.setLogLevel("ERROR")

orders = spark.createDataFrame(
    [(10, 1, 50.0), (11, 1, 70.0), (12, 2, 20.0), (13, 9, 99.0), (14, None, 5.0)],
    "order_id INT, customer_id INT, amount DOUBLE")
customers = spark.createDataFrame(
    [(1, "Asha", "IN"), (2, "Ben", "UK"), (3, "Chen", "UK"), (None, "Ghost", "XX")],
    "customer_id INT, name STRING, country STRING")

def explain_text(df):
    buf = io.StringIO()
    with contextlib.redirect_stdout(buf):
        df.explain()
    return buf.getvalue()

def plan(df):
    text = re.sub(r"#\d+L?", "", explain_text(df))
    text = re.sub(r", \[plan_id=\d+\]", "", text)
    print(re.sub(r"\[file:[^\]]*\]", "[...]", text).strip())

def strategy(df):
    found = re.findall(r"(BroadcastHashJoin|SortMergeJoin|ShuffledHashJoin|"
                       r"BroadcastNestedLoopJoin|CartesianProduct)", explain_text(df))
    return found[0] if found else None
```

## Joins in Spark SQL

### Join types

`df.join(other, on, how)` supports every SQL join type. `on` can be a column name, a list of names or a boolean Column expression; `how` defaults to `"inner"`.

```python
for how in ["inner", "left", "right", "full", "left_semi", "left_anti"]:
    j = orders.join(customers, on="customer_id", how=how)
    print(f"{how:10}", j.count(), j.columns)
```

```text
inner      3 ['customer_id', 'order_id', 'amount', 'name', 'country']
left       5 ['customer_id', 'order_id', 'amount', 'name', 'country']
right      5 ['customer_id', 'order_id', 'amount', 'name', 'country']
full       7 ['customer_id', 'order_id', 'amount', 'name', 'country']
left_semi  3 ['customer_id', 'order_id', 'amount']
left_anti  2 ['customer_id', 'order_id', 'amount']
```

| `how` | Returns |
|-------|---------|
| `inner` | Rows with a match on both sides |
| `left` / `left_outer` | All left rows; right columns NULL where there is no match |
| `right` / `right_outer` | All right rows |
| `full` / `full_outer` | All rows from both sides |
| `left_semi` | Left rows that have at least one match; left columns only, never duplicated |
| `left_anti` | Left rows with **no** match; left columns only |
| `cross` (or `crossJoin`) | Every combination: rows multiply |

`left_semi` is the DataFrame form of `WHERE EXISTS`, and `left_anti` of `WHERE NOT EXISTS`. Both are cheaper and safer than a left join followed by a filter, because they never add columns or duplicate rows.

The full outer join shows how NULL keys behave:

```python
orders.join(customers, "customer_id", "full").orderBy("order_id").show()
```

```text

|       NULL|    NULL|  NULL|Ghost|     XX|

|          1|      10|  50.0| Asha|     IN|
|          1|      11|  70.0| Asha|     IN|
|          2|      12|  20.0|  Ben|     UK|

|       NULL|      14|   5.0| NULL|   NULL|
```

Order 14 (NULL customer) and customer Ghost (NULL key) appear on **separate** rows: NULL never equals NULL in a join condition.

### Joining on names vs expressions

Joining on a column **name** (or list of names) keeps one copy of the key. Joining on an **expression** keeps both, and an unqualified reference to the key then fails:

```python
o, c = orders.alias("o"), customers.alias("c")
expr_join = o.join(c, F.col("o.customer_id") == F.col("c.customer_id"), "left")
print(expr_join.columns)
try:
    expr_join.select("customer_id").show()
except Exception as e:
    print(type(e).__name__, str(e).split(",")[0])
expr_join.select("o.order_id", "c.name", F.col("o.customer_id")).orderBy("order_id").show()
```

```text
['order_id', 'customer_id', 'amount', 'customer_id', 'name', 'country']
AnalysisException [AMBIGUOUS_REFERENCE] Reference `customer_id` is ambiguous
+--------+----+-----------+
|order_id|name|customer_id|
+--------+----+-----------+
|      10|Asha|          1|
|      11|Asha|          1|
|      12| Ben|          2|
|      13|NULL|          9|
|      14|NULL|       NULL|
+--------+----+-----------+
```

Use expressions when the key names differ or the condition is not plain equality, and give each DataFrame an `alias` so columns can be qualified. Aliases are essential for **self-joins** (an employee table joined to itself for managers), where both sides otherwise have identical column references.

### Null-safe joins

When NULL should match NULL (for example, composite keys where some parts are optional), use `eqNullSafe` (SQL `<=>`):

```python
print(orders.join(customers, orders.customer_id == customers.customer_id).count())
print(orders.join(customers, orders.customer_id.eqNullSafe(customers.customer_id)).count())
```

```text
3
4
```

The fourth row is order 14 matched with Ghost. That is rarely what you want for real business keys, so use it deliberately.

### Non-equi joins

Joins on ranges (an amount falling into a price band, an event inside a session window) are allowed, but without an equality condition Spark cannot hash or sort by key, so it falls back to a **nested loop** over every pair. That is fine only when one side is tiny and broadcast:

```python
tiers = spark.createDataFrame([("bronze", 0.0, 30.0), ("silver", 30.0, 60.0), ("gold", 60.0, 1e9)],
                              "tier STRING, lo DOUBLE, hi DOUBLE")
banded = orders.join(F.broadcast(tiers), (orders.amount >= tiers.lo) & (orders.amount < tiers.hi))
banded.select("order_id", "amount", "tier").orderBy("order_id").show()
print(strategy(banded))
```

`COUNT(o.order_id)` (not `COUNT(*)`) gives 0 for Chen, because the unmatched row has a NULL `order_id`. Spark SQL also accepts `LEFT SEMI JOIN` and `LEFT ANTI JOIN` directly, and rewrites `EXISTS` / `NOT EXISTS` subqueries into those joins.

### Pitfalls

- **Fan-out.** If the right side has several rows per key, every matching left row is repeated. Check key uniqueness before joining (`groupBy(key).count().filter("count > 1")`), especially on dimension tables that are supposed to be unique.
- **Filtering a left join in `WHERE`.** A condition on a right-side column in `WHERE` (`WHERE o.amount > 10`) removes the NULL rows and silently turns the left join into an inner join. Put it in the `ON` clause, or filter the right side before joining.
- **`NOT IN` with NULLs.** In SQL, `NOT IN (subquery)` returns nothing if the subquery contains a NULL. Prefer `NOT EXISTS` or `left_anti`.
- **Accidental cross joins.** A join condition that references only one side multiplies rows; Spark allows explicit cross joins, so check row counts.

### In interviews

Expect "find customers who never ordered" (anti join), "why did my row count grow after a join?" (fan-out), and "what is the difference between a left semi join and an inner join?" (semi returns left columns only and never duplicates left rows).

## Broadcast hash join

### What it is

In a **broadcast hash join**, Spark collects the small side to the driver, sends a full copy to every executor and builds an in-memory hash table from it. Each partition of the large side is then joined locally by probing the hash table. **The large side is never shuffled**, which removes the most expensive part of a join.

Spark broadcasts automatically when it estimates that one side is smaller than `spark.sql.autoBroadcastJoinThreshold` (10 MB by default; `-1` disables automatic broadcasting). You can force it with `F.broadcast(df)` or a `BROADCAST` hint.

### Worked example

Size estimates come from statistics. For Parquet files, Spark knows the file sizes, so it broadcasts the small dimension table:

```python
spark.conf.set("spark.sql.adaptive.enabled", "false")   # show the planned strategy only
big = spark.range(0, 200_000).select(
    F.col("id").alias("order_id"), (F.col("id") % 5000).alias("customer_id"), (F.col("id") % 97).alias("amount"))
dim = spark.range(0, 5000).select(F.col("id").alias("customer_id"), (F.col("id") % 3).alias("segment"))
bpath, dpath = warehouse + "/big", warehouse + "/dim"
big.write.mode("overwrite").parquet(bpath)
dim.write.mode("overwrite").parquet(dpath)
bigf, dimf = spark.read.parquet(bpath), spark.read.parquet(dpath)
print(strategy(bigf.join(dimf, "customer_id")))
plan(bigf.join(dimf, "customer_id"))
```

```text
BroadcastHashJoin
== Physical Plan ==
*(2) Project [customer_id, order_id, amount, segment]
+- *(2) BroadcastHashJoin [customer_id], [customer_id], Inner, BuildRight, false, false
   :- *(2) Filter isnotnull(customer_id)
   :  +- *(2) ColumnarToRow
   :     +- FileScan parquet [order_id,customer_id,amount] Batched: true, DataFilters: [isnotnull(customer_id)], Format: Parquet, Location: InMemoryFileIndex(1 paths)[...], PartitionFilters: [], PushedFilters: [IsNotNull(customer_id)], ReadSchema: struct<order_id:bigint,customer_id:bigint,amount:bigint>
   +- BroadcastExchange HashedRelationBroadcastMode(List(input[0, bigint, false]),false)
      +- *(1) Filter isnotnull(customer_id)
         +- *(1) ColumnarToRow
            +- FileScan parquet [customer_id,segment] Batched: true, DataFilters: [isnotnull(customer_id)], Format: Parquet, Location: InMemoryFileIndex(1 paths)[...], PartitionFilters: [], PushedFilters: [IsNotNull(customer_id)], ReadSchema: struct<customer_id:bigint,segment:bigint>
```

`BuildRight` means the right side (`dimf`) is the one broadcast and hashed. There is a `BroadcastExchange` on the small side and **no `Exchange hashpartitioning`** on the large side.

Spark can only estimate what it can measure. DataFrames built from local Python data (`createDataFrame`) or from complex upstream plans may have no useful size estimate, so they are not broadcast at planning time even when tiny:

```python
print(strategy(orders.join(customers, "customer_id")))
print(strategy(orders.join(F.broadcast(customers), "customer_id")))
```

```text
SortMergeJoin
BroadcastHashJoin
```

### Which side can be broadcast

The broadcast side must be the side whose unmatched rows are **not** needed in the output, because each executor only sees its own slice of the other side:

```python
print(strategy(orders.join(F.broadcast(customers), "customer_id", "left")))
print(strategy(orders.join(F.broadcast(customers), "customer_id", "right")))
print(strategy(orders.join(F.broadcast(customers), "customer_id", "full")))
```

```text
BroadcastHashJoin
SortMergeJoin
SortMergeJoin
```

| Join type | Side that can be broadcast |
|-----------|----------------------------|
| inner | Either |
| left outer, left semi, left anti | Right only |
| right outer | Left only |
| full outer | Neither (as a hash join) |

When the hint cannot be honoured, Spark ignores it and logs a warning; it does not fail.

### Pitfalls

- **Broadcasting something that is not small.** The broadcast table is collected to the driver and held in memory on every executor. A "small" table that grows to gigabytes causes driver out-of-memory errors or broadcast timeouts (`spark.sql.broadcastTimeout`, 300 seconds by default). Raise the threshold carefully, and never hint a table whose size you do not control.
- **The estimate is of the plan, not the file.** A filter or a projection may make a large table small; Spark's estimate after filters can be off. AQE fixes many of these cases at run time (below).
- **Repeated broadcasts.** A broadcast is rebuilt for each query that uses it; caching the small table helps when it comes from an expensive computation.

### In interviews

"When would you use a broadcast join?" Answer: when one side comfortably fits in executor memory; the large side is not shuffled; it cannot broadcast the preserved side of an outer join; and it can fail with OOM or timeouts if the small side grows. See the [interview answer](/interview/pyspark/broadcast-join/).

## Sort-merge join and how to tune it

### How it works

A **sort-merge join** is Spark's default for joining two large tables on equality keys (`spark.sql.join.preferSortMergeJoin` is `true`). It runs in three steps:

1. **Shuffle** both sides by the join key (`Exchange hashpartitioning`) so that equal keys from both tables land in the same partition number.
2. **Sort** each partition by the key.
3. **Merge**: walk both sorted partitions together, like merging two sorted lists, emitting matches.

```python
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "-1")
print(strategy(bigf.join(dimf, "customer_id")))
plan(orders.join(customers, "customer_id"))
```

```text
SortMergeJoin
== Physical Plan ==
*(5) Project [customer_id, order_id, amount, name, country]
+- *(5) SortMergeJoin [customer_id], [customer_id], Inner
   :- *(2) Sort [customer_id ASC NULLS FIRST], false, 0
   :  +- Exchange hashpartitioning(customer_id, 4), ENSURE_REQUIREMENTS
   :     +- *(1) Filter isnotnull(customer_id)
   :        +- *(1) Scan ExistingRDD[order_id,customer_id,amount]
   +- *(4) Sort [customer_id ASC NULLS FIRST], false, 0
      +- Exchange hashpartitioning(customer_id, 4), ENSURE_REQUIREMENTS
         +- *(3) Filter isnotnull(customer_id)
            +- *(3) Scan ExistingRDD[customer_id,name,country]
```

It scales to any size because sorted partitions can spill to disk, but you pay for a full shuffle of **both** sides plus two sorts. Note the `Filter isnotnull(customer_id)` that Spark adds for an inner join: NULL keys can never match, so they are dropped before the shuffle.

### Tuning levers

| Lever | What it does |
|-------|--------------|
| `spark.sql.shuffle.partitions` (default 200) | Number of partitions after the shuffle. Too few: huge partitions that spill; too many: tiny tasks with overhead. Size so that each post-shuffle partition is roughly in the 100-200 MB range, or let AQE coalesce. |
| **AQE** (`spark.sql.adaptive.enabled`, default `true`) | Re-plans at run time from real shuffle statistics: coalesces small partitions, switches to a broadcast join when one side turns out small, and splits skewed partitions. |
| **AQE skew join** (`spark.sql.adaptive.skewJoin.enabled`, default `true`) | A partition is treated as skewed when it is more than `skewedPartitionFactor` (default 5) times the median **and** larger than `skewedPartitionThresholdInBytes` (default 256 MB); Spark splits it and replicates the matching side. |
| Filter and project early | Fewer rows and columns to shuffle. |
| Pre-aggregate before the join | Join daily totals instead of raw events when the result allows it. |
| Handle NULL or hot keys | For outer joins, NULL keys are shuffled into one partition; split them off and union them back. Salt genuinely hot keys. |
| Bucketing | Pays the shuffle once at write time (next sections). |

AQE at work: the same small, unmeasured DataFrames planned as a sort-merge join become a broadcast join once the shuffle reveals their real size.

```python
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "10485760")
j = orders.join(customers, "customer_id")
print("before execution:", strategy(j))
j.collect()
print("final plan:", strategy(j), "| AQE final:", "isFinalPlan=true" in explain_text(j))
```

```text
before execution: SortMergeJoin
final plan: BroadcastHashJoin | AQE final: True
```

AQE cannot avoid the shuffles that already ran to measure the data, but it can skip the sort and merge and use local shuffle reads instead. See [Adaptive Query Execution](/spark/adaptive-query-execution/) and [partitions, shuffles and skew](/spark/partitions-shuffles-skew/) for skew and salting in depth.

### Pitfalls

- **Spill**: in the Spark UI, large "Spill (disk)" values on the join stage mean partitions are too big. Increase the shuffle partition count or fix skew.
- **One straggler task**: a hot key. AQE skew handling helps for inner joins and the non-preserved side of outer joins; it cannot split a skewed key on the side whose rows must all be kept in some outer-join cases, so salting may still be needed.
- **Join key type mismatch** (`int` vs `string`) forces a cast on one side and can prevent pushdown and bucketing; align types first.

### In interviews

"Walk me through a sort-merge join" and "your join stage has one task running for an hour, what do you do?" The strong answer: shuffle, sort, merge; diagnose skew in the Spark UI; check NULL keys; use AQE skew join, broadcast, or salting.

## How Spark selects a join strategy

### The decision order

For an **equi-join**, Spark's planner tries strategies in roughly this order:

1. **Hints**, in priority order `BROADCAST` > `MERGE` > `SHUFFLE_HASH` > `SHUFFLE_REPLICATE_NL`, if the join type allows them.
2. **Broadcast hash join** if one buildable side's estimated size is below `autoBroadcastJoinThreshold`.
3. **Shuffle hash join** if `preferSortMergeJoin` is `false` and one side is small enough to build a per-partition hash map, and much smaller than the other.
4. **Sort-merge join** if the keys are sortable (the usual result for two large tables).
5. Otherwise a **cartesian product** or **broadcast nested loop join**.

For a **non-equi join** (no equality condition), only broadcast nested loop join and cartesian product are possible.

At run time, AQE can still change a sort-merge join into a broadcast join, or into a shuffle hash join when every post-shuffle partition fits under `spark.sql.adaptive.maxShuffledHashJoinLocalMapThreshold` (0 by default, which disables that conversion).

### Hints

```python
spark.conf.set("spark.sql.adaptive.enabled", "false")
for hint in ["broadcast", "merge", "shuffle_hash", "shuffle_replicate_nl"]:
    print(f"{hint:22}", strategy(orders.join(customers.hint(hint), "customer_id")))
print(strategy(spark.sql(
    "SELECT /*+ BROADCAST(c) */ * FROM orders o JOIN customers c ON o.customer_id = c.customer_id")))
print(strategy(orders.join(customers, orders.customer_id < customers.customer_id)))
```

```text
broadcast              BroadcastHashJoin
merge                  SortMergeJoin
shuffle_hash           ShuffledHashJoin
shuffle_replicate_nl   CartesianProduct
BroadcastHashJoin
CartesianProduct
```

### Comparison

| Strategy | Shuffle | Memory need | Best for | Join types |
|----------|---------|-------------|----------|------------|
| Broadcast hash join | None on the large side | Whole small side on every executor and the driver | Large fact joined to a small dimension | All except full outer (build side restrictions) |
| Shuffle hash join | Both sides | Hash map of one side's partition | One side much smaller but too big to broadcast; avoids sorting | Most; build side restrictions apply |
| Sort-merge join | Both sides, plus sort | Low; can spill | Two large tables | All equi-joins |
| Broadcast nested loop join | None | Small side on every executor | Non-equi joins with a tiny side | All |
| Cartesian product | Both sides | High; output is rows × rows | Explicit cross joins only | Inner / cross |

### Pitfalls and interview angle

- Hints override statistics, so a hint written for last year's data volume can hurt today. Prefer accurate statistics (`ANALYZE TABLE ... COMPUTE STATISTICS` for catalog tables) and AQE, and keep hints for cases you have measured.
- Check the **physical plan**, not the code: `explain()` or the SQL tab of the Spark UI shows which strategy actually ran (for AQE, look at the final plan).
- Interviewers like "how does Spark decide between broadcast and sort-merge?" Mention the size threshold, statistics, hints, join-type restrictions and AQE run-time re-planning.

## Bucketing in Spark

### What it is

**Bucketing** splits a table into a fixed number of buckets by hashing one or more columns at write time, and records the bucket spec in the catalog. Rows with the same key always end up in the same bucket number. Later queries that join or aggregate on that key can use the layout instead of shuffling. You pay the shuffle **once**, when writing, instead of in every query.

Bucketing differs from partitioning: `partitionBy` creates one folder per value (good for low-cardinality filter columns like a date), while `bucketBy` creates a fixed number of files per partition by hash (good for high-cardinality join keys like a customer ID).

### Creating bucketed tables

Bucketing needs a table in a catalog, so you must use `saveAsTable`; a plain `save(path)` does not record the bucket spec.

```python
(big.write.mode("overwrite").bucketBy(8, "customer_id").sortBy("customer_id")
    .saveAsTable("orders_bucketed"))
(dim.write.mode("overwrite").bucketBy(8, "customer_id").sortBy("customer_id")
    .saveAsTable("customers_bucketed"))
(spark.sql("DESCRIBE EXTENDED orders_bucketed")
      .filter("col_name IN ('Num Buckets','Bucket Columns','Sort Columns')").show())
import os
print(len([f for f in os.listdir(warehouse + "/orders_bucketed") if f.endswith(".parquet")]))
```

```text
+--------------+---------------+-------+
|      col_name|      data_type|comment|
+--------------+---------------+-------+
|   Num Buckets|              8|       |
|Bucket Columns|[`customer_id`]|       |
|  Sort Columns|[`customer_id`]|       |
+--------------+---------------+-------+

16
```

8 buckets produced **16 files**: each writing task writes its own file for every bucket it holds rows for, so the file count can reach `tasks × buckets`. With 200 tasks and 512 buckets that is up to 102,400 small files. A common fix is to `repartition(n_buckets, "customer_id")` before writing, so that each task holds exactly one bucket.

### Pitfalls

- **Bucket specs are a Spark (Hive-style catalog) feature.** Other engines may not read or honour them, and Spark's bucket hash is not the same as Hive's.
- **Changing the bucket count means rewriting the table.**
- **Delta Lake does not support `bucketBy`**; for Delta tables, use partitioning, Z-ordering or liquid clustering instead (covered in the Delta Lake performance lesson).
- **Small-file explosion** as shown above.

### In interviews

"What is the difference between partitioning and bucketing?" Partitioning: folders by value, used for pruning on filters. Bucketing: fixed number of hashed files, used to avoid shuffles in joins and aggregations on high-cardinality keys. Mention the `saveAsTable` requirement and the file-count trap.

## Bucketed joins

### What makes a join shuffle-free

When both tables are bucketed on the join key **with the same number of buckets**, bucket *i* of one table can only match bucket *i* of the other. Spark reads them as already partitioned and skips the `Exchange` on both sides:

```python
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "-1")
bj = spark.table("orders_bucketed").join(spark.table("customers_bucketed"), "customer_id")
plan(bj)
```

### Conditions for a bucketed join

- Both tables are bucketed on the **join keys** (all of them, in the same order) and read as catalog tables (`spark.table`, SQL), not as paths.
- **Same number of buckets.** With different counts Spark shuffles at least one side, unless `spark.sql.bucketing.coalesceBucketsInJoin.enabled` (off by default) lets it coalesce the larger count when one is a multiple of the other.
- **Same key types** on both sides; a cast breaks the match.
- `spark.sql.sources.bucketing.enabled` must be `true` (the default). Spark may also decide not to use bucketed scans when the query gains nothing from them (`spark.sql.sources.bucketing.autoBucketedScan.enabled`).

### Pitfalls

- **Benefit only for repeated joins.** Bucketing costs a shuffle at write time; it pays off when the same large tables are joined or aggregated on the same key many times.
- **Too many buckets** for the data volume means tiny files; too few means huge buckets and less parallelism on read (one task per bucket).
- **Bucketed tables with appends** keep adding files per bucket, so periodic compaction is needed.

### In interviews

"How can you join two huge tables repeatedly without shuffling every time?" Bucket both on the join key with the same bucket count, read them as tables, and confirm with `explain()` that no `Exchange` remains. Mention the alternatives: broadcast when one side is small, and storage-partitioned joins in table formats that support them.

## Practice questions

<details>
<summary>Find all customers who have never placed an order, in DataFrame code and in SQL.</summary>

`customers.join(orders, "customer_id", "left_anti")`, or in SQL `SELECT * FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id)`. Avoid `NOT IN` with a subquery that can contain NULLs, which returns no rows.

</details>

<details>
<summary>Why can't Spark broadcast the left table of a left outer join?</summary>

Every left row must appear in the output, including those with no match. If the left side were broadcast, each executor would see all left rows but only its slice of the right side, so it could not know whether a left row matched on another executor. Only the right (non-preserved) side can be broadcast for a left join.

</details>

<details>
<summary>A tiny lookup DataFrame built with createDataFrame is joined with a sort-merge join. Why, and what can you do?</summary>

Spark has no reliable size estimate for in-memory or complex DataFrames at planning time, so it does not choose a broadcast. Use `F.broadcast(lookup)` when you know it is small, rely on AQE to switch at run time after the shuffle, or materialise the lookup as a table or files so statistics exist.

</details>

<details>
<summary>Explain the steps of a sort-merge join and where its cost comes from.</summary>

Both sides are shuffled by the join key so equal keys share a partition, each partition is sorted by key, then the sorted streams are merged. The cost is the network and disk I/O of shuffling both tables, plus the sorts and any spill. Skewed keys make single partitions much larger than others.

</details>

<details>
<summary>What is the difference between partitioning and bucketing a table?</summary>

Partitioning writes a folder per distinct value of low-cardinality columns and lets queries skip folders through partition pruning. Bucketing hashes a (usually high-cardinality) column into a fixed number of buckets recorded in the catalog, so joins and aggregations on that column can avoid shuffles. They can be combined.

</details>

<details>
<summary>Two tables are bucketed on customer_id, but the join still shows an Exchange. What would you check?</summary>

That both have the same bucket count, are bucketed on exactly the join keys with matching types, are read as catalog tables rather than file paths, and that bucketing is enabled. Also check whether one side went through an operation that changed its partitioning before the join.

</details>

<details>
<summary>When would a shuffle hash join beat a sort-merge join?</summary>

When one side is much smaller than the other but too big to broadcast, and each of its post-shuffle partitions fits comfortably in memory as a hash map. It skips the sort step. It can run out of memory if a partition of the build side is too large, which is why sort-merge is the default.

</details>

## Key takeaways

- Join on column names to avoid ambiguous columns; use aliases for expressions and self-joins; use `left_semi` and `left_anti` for existence checks.
- NULL keys never match in equi-joins, and duplicate keys multiply rows: check both before joining.
- Broadcast hash joins avoid shuffling the large side but need the small side in memory everywhere, and cannot broadcast the preserved side of an outer join.
- Sort-merge joins shuffle and sort both sides; tune them with shuffle partitions, AQE skew handling, early filtering and NULL-key handling.
- Spark chooses strategies from hints, size estimates and join type, and AQE can re-plan at run time; always confirm with `explain()`.
- Bucketing pays the shuffle once at write time; bucketed joins need matching keys, types and bucket counts on catalog tables.
