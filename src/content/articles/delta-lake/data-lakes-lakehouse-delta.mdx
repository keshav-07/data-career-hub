A data lake stores files cheaply in object storage. A lakehouse adds the reliability of a warehouse on top of those files through an open **table format** such as Delta Lake. This guide connects the pieces.

## 1. Lakes, warehouses and lakehouses

Lakes are flexible and cheap but lack transactions and enforced schemas; warehouses are reliable but keep data in their own storage; lakehouses keep data in open formats on object storage while adding transactions and governance.

Read: [Lake vs warehouse vs lakehouse](/data-warehousing/lake-vs-warehouse-vs-lakehouse/) · Practise: [When to choose each](/interview/data-engineering/lake-warehouse-lakehouse/)

## 2. File formats

Use columnar Parquet for analytical data, row-based Avro for messages, and treat JSON and CSV as landing formats only.

Read: [JSON vs Parquet](/delta-lake/json-vs-parquet/) · [Parquet vs Avro vs ORC](/delta-lake/parquet-vs-avro-vs-orc/) · Practise: [Parquet internals](/interview/delta-lake/parquet-internals/)

## 3. Table formats and the transaction log

Delta Lake writes Parquet data files plus a `_delta_log` of commits. That log provides atomic writes, consistent snapshots, optimistic concurrency, time travel and row-level `MERGE`, `UPDATE` and `DELETE`. Apache Iceberg and Apache Hudi solve the same problem with different metadata designs.

Read: [Delta Lake transactions, schema evolution and time travel](/delta-lake/transactions-schema-evolution/) · [Delta vs plain Parquet tables, Iceberg and Hudi](/delta-lake/delta-vs-traditional-lake-tables/) · Practise: [What Delta Lake solves](/interview/delta-lake/what-delta-lake-solves/) · [Delta vs Iceberg vs Hudi](/interview/delta-lake/delta-vs-iceberg-vs-hudi/) · [Time travel uses and limits](/interview/delta-lake/time-travel-use-cases-limits/)

## 4. MERGE, CDC and streaming

`MERGE` applies inserts, updates and deletes from a change feed in one commit and can maintain a Type 2 dimension. The change data feed exposes row-level changes to downstream jobs, and Delta tables work as exactly-once streaming sinks and as streaming sources.

Read: [MERGE, change data feed and streaming](/delta-lake/merge-upserts-change-data-feed/) · Practise: [How MERGE works and why concurrent MERGEs fail](/interview/delta-lake/delta-merge-internals-conflicts/)

## 5. Schema enforcement and evolution

Reject mismatched writes by default; evolve schemas deliberately, preferring additive changes and expand-and-contract migrations for breaking ones.

Read: [Schema evolution patterns](/delta-lake/schema-evolution-patterns/) · Practise: [When schema evolution is safe](/interview/delta-lake/schema-evolution-safety/)

## 6. Maintenance and layout

Compact small files with `OPTIMIZE`, cluster data on common filters (liquid clustering on new tables, Z-order on older ones), use deletion vectors for cheap row-level changes, and `VACUUM` with a retention that respects time travel and long readers.

Read: [OPTIMIZE, Z-ordering, VACUUM and liquid clustering](/delta-lake/optimize-zorder-vacuum-liquid-clustering/) · [Partitioning, clustering and data layout](/data-warehousing/partitioning-clustering-data-layout/) · Practise: [Z-order vs liquid clustering](/interview/delta-lake/optimize-zorder-vs-liquid-clustering/) · [VACUUM risks](/interview/delta-lake/vacuum-retention-risks/)

## Medallion layers

Organise tables into bronze (raw), silver (cleaned and conformed) and gold (business models). Each layer reads only the previous one and can be rebuilt.

Read: [Databricks workspace, jobs and lakehouse](/databricks/workspace-jobs-lakehouse/) · [Modelling methodologies: medallion](/data-warehousing/modeling-methodologies/)
